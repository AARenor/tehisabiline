API pentesti kontrollnimekiri

Kontrollnimekiri seob OWASP API Security Top 10 (2023) riskid kontrolli ja tõendiga, mida raportist oodata, ning loetleb kordustesti punktid. API turvatestimise juhend – autentimine, rollid, testkontod ja ostmise küsimused – on API turvatestimise juhendis.

Mis see kontrollnimekiri on?

See leht on tööleht, mille järgi API pentest päringute kaupa läbi viiakse: iga OWASP API Security Top 10 (2023) kategooria kohta on kirjas rike, objekti ja rolli paar, tõend ja kordustingimuse sõnastus. Nimekiri ei ole skanniraport ega vastavussertifikaat: läbitud rida tähendab, et kontroll tehti ja tulemus dokumenteeriti, mitte et API on turvaline. Nimekirja täidab testija koos tellijaga, sest oodatud õigused tulevad sinu tootest, mitte OWASP-ist.

Kuidas kontrollnimekirja kasutada

Tööüksus on üks API: üks host, üks versioon ja üks keskkond korraga. Kui samast koodist jookseb mitu versiooni või keskkonda, täidetakse igaühe kohta eraldi leht, sest OWASP kohtleb vananenud versiooni eraldi riskina (API9).

Üks rida vastab ühele kontrollile: üks otspunkt, üks meetod, üks roll ja üks objekt. Rida, mis katab mitu rolli korraga, kaob raportist esimesena, sest hiljem ei ole näha, millise rolliga tulemus saadi.

OWASP API Top 10 (2023): kümme kategooriat lahti seletatud

OWASP API Security Top 10 (2023) kirjeldab riskikategooriad, mitte kohustuslikku testipaketti. Allolev tabel seob iga kategooria kontrolli ja tõendiga ning jaotised selle all ütlevad iga kategooria kohta, milline rike seda iseloomustab, milline objekti ja rolli paar selle nähtavale toob, milline tõend kontrolli tõestab ja millal see kordustestis läbituks loetakse.

API1:2023 BOLA – objektipõhine autoriseerimine

Rike: otspunkt võtab objektiviite kliendilt ja tagastab objekti, kontrollimata, kas päringu tegijal on sellele õigus. Paar: kaks rentnikku ja kaks rolli ühes API-s; rentniku A tavakasutaja pärib rentniku B objektiviite. Tõend: päring, vastuse kood ja keha. Kordustest: sama päring sama rolli ja objektiga; paranemist tõestab serverist tulev keeld.

API2:2023 Autentimine

Rike: sisselogimis- või taastamisvoog lubab võtta teise kasutaja identiteedi, näiteks kontrollimata tokeni allkirja või aegumise või piiramata parooliproovide tõttu. Paar: kaks testkontot; A tokeniga proovitakse B seanssi ja B parooli taastamist. Tõend: katse kirjeldus, vastuse koodid ja tokeni eluiga. Kordustest: vana token keeldub ja taastamisvoog on sama rangelt piiratud kui sisselogimine.

API3:2023 BOPLA – väljade tasemel õigused

Rike: vastus sisaldab välju, mida roll ei vaja, või muutmispäring lubab muuta välja, mida roll ei tohi puutuda. Paar: tavakasutaja ja administraator sama objektiga; kehasse lisatakse väli (hind, staatus, roll) ja vaadatakse, kas server võtab selle vastu. Tõend: keha enne ja pärast, vastuse väljad, kõrvalmõju. Kordustest: sama keha ei tohi väärtust muuta; oluline on tulemus, mitte üks kindel vastuse kood.

API4:2023 Ressursitarbimine

Rike: puudub piirang, mis hoiab ära ühe või korduva päringu tekitatud koormuse ja kulu: lehekülje suurus, faili maht, operatsioonide arv päringus, kolmanda teenuse kululagi. Paar: üks tavakasutaja token ja üks otspunkt, mis kutsub tasulist teenust. Tõend: piirangu puudumine ja mõju, näiteks vastuse maht või väliskutsete arv. Kordustest: sama päring peatub piirangul ja vastus ütleb, mis piir ületati.

API5:2023 BFLA – funktsioonipõhine autoriseerimine

Rike: funktsioon, mis peaks olema ainult teatud rollile, vastab ka teisele rollile või teisele HTTP-meetodile. Paar: tavakasutaja token ja administraatori otspunkt; proovitakse ka meetodi vahetust GET-ist DELETE-iks. Tõend: roll, otspunkt, meetod ja vastus. Kordustest: sama roll saab sama otspunkti pealt keelu; kontrolli ka naaberotspunkti, sest administraatori rajad ei ole alati URL-i järgi äratuntavad.

API6:2023 Ärivoog – piiramata ligipääs tundlikele ärivoogudele

Rike: ärivoo, näiteks ost, broneering või kommentaar, on automatiseeritav nii, et see kahjustab ettevõtet, kuigi iga üksik päring on korrektne. Paar: tavakasutaja roll ja kaks rentnikku, et näha nii kliendi kui platvormi mõju. Tõend: sammud, korduste arv ja äriline mõju. Kordustest: sama voog sama arvu sammudega ei õnnestu enam automaatselt ja piirang on äriliselt põhjendatud.

API7:2023 SSRF

Rike: API toob kasutaja antud URL-ilt ressursi sihtkohta piiramata, nii et päring jõuab sisemisse teenusesse või pilve haldusliidesesse. Paar: tavakasutaja roll ja otspunkt, mis võtab URL-i: webhook, pildi link, eelvaade või SSO. Tõend: sihtkoha piirang, vastus ja vastuse aeg; pimeda SSRF-i korral eraldi tõend. Kordustest: sama URL on blokeeritud ja lubatud sihtkohtade loend on dokumenteeritud.

API8:2023 Seadistus

Rike: seadistus jätab alles selle, mida ei vaja: liigsed HTTP-meetodid, puuduv TLS, vale CORS, stack trace'iga veateated, puuduvad cache-päised. Paar: anonüümne päring ja tavakasutaja; mõlema rolli päiseid ja veateateid võrreldakse. Tõend: päised, veateade ja seadistuse asukoht. Kordustest: samad päringud annavad korrastatud päise ja neutraalse veateate; kontrolli ka vahendajaid, sest ahela lülid võivad päringut erinevalt tõlgendada.

API9:2023 Varud

Rike: keegi ei tea, millised hostid, versioonid ja keskkonnad on olemas, ning vana versioon jääb turvakontrollidest ilma. Paar: vana versiooni host ja tavakasutaja token, mis on välja antud uue versiooni jaoks. Tõend: hostide ja versioonide loend, keskkonna silt, ligipääsu tulemus. Kordustest: vana host on suletud või samade kontrollidega ning loend ja dokumentatsioon ühtivad.

API10:2023 Tarbimine

Rike: API usaldab kolmanda teenuse vastust nagu oma sisemist andmet, valideerimata seda enne töötlemist. Paar: tavakasutaja sisend, mis jõuab kolmanda teenuse kaudu tagasi andmebaasi või uude päringusse. Tõend: andmevoog, valideerimise puudumine ja vastuse mõju. Kordustest: sama sisend puhastatakse või lükatakse tagasi ning ümbersuunamised on lubatud sihtkohtade loendis.

Testandmed ja rollid: miks kaks rentnikku ja kolm rolli

OWASP WSTG soovitab objektiviiteid testida vähemalt kahe kasutajaga, kellel on erinevad objektid, ja vajadusel kõrgemate õigustega kasutajaga. Nii ei pea testija objektinumbreid arvama.

Mitme rentnikuga API-s tähendab see kahte rentnikku, sest piir kehtib ka kliendi tasandil: rentniku administraator tohib oma rentnikus rohkem kui tavakasutaja, aga mitte teise rentniku andmetes. Kolm rolli on alustamise miinimum: anonüümne päring, tavakasutaja ja administraator. Kui tootes on platvormi administraator või tugiisik, kes näeb klientide andmeid, on see neljas roll.

Testkontod loob tellija ja need on eraldi kontod, mida keegi teine samal ajal ei kasuta. Tokenid antakse üle turvalises kanalis, kehtivad testimise aja ja tühistatakse pärast tööd. Tõenditesse ei kopeerita tokeneid ega paroole, sest tokeni aegumine on OWASP-i järgi osa testist.

Eelistatud on testkeskkond sünteetiliste andmetega. OWASP märgib, et tootmisandmeid ei tohiks kasutada mitteproduktsiooni paigaldustes, ja kui see on vältimatu, tuleb neid otspunkte käsitleda tootmisena. Tootmises testimisel lepitakse kirjalikult kokku ajavahemik ja päringute ülempiir; ootamatu ligipääsu korral uurimine lõpetatakse ja leid fikseeritakse.

Hindamine, raport ja kordustest

Raskusaste ei tule kategooria numbrist. OWASP annab iga kategooria juures üldise hinnangu ärakasutamise lihtsusele, levimusele ja mõjule, mis ei ütle midagi sinu süsteemi kohta. CVSS v4.0 jaotab raskusastme ärakasutamise eeldusteks ja mõjuks ning vaatab mõju kahes osas: mõju haavatavale süsteemile ja mõju teistele süsteemidele. Rea puhul loe sama: kui kaugele leid ulatub ja kui palju see avab.

Kolm küsimust eristavad kõrge riskiga rida tavalisest: kas leid on autenditud kasutajale kättesaadav ilma eriettevalmistuseta, kui paljusid kliente see puudutab ja kas see annab õigusi juurde. Kõige rängem on tavaliselt rida, kus üks roll näeb teise rentniku andmeid või muudab neid.

Leiuks saab rida siis, kui sellele lisandub mõju, tõenäosus ja parandusettepanek. NIST SP 800-115 järgi sisaldab raport metoodikat, tulemusi, analüüsi ja parandusplaani ning võib vajada eri kujul eri lugejatele.

Mida kordustest peab näitama

  1. Vali leiud: kõik kriitilised ja need, mille parandus muutis autentimist või õigusi.
  2. Korda sama päringut: sama roll, sama rentnik ja sama objekt, et tulemus oleks võrreldav.
  3. Kontrolli regressiooni: kas parandus ei avanud teist teed sama objekti juurde.
  4. Dokumenteeri: märgi, kas leid on suletud, osaliselt parandatud või endiselt avatud.

NIST SP 800-115 märgib, et testija saab parandust kontrollida ainult siis, kui ta kordab algset testi peegelkujutisena. Seepärast ei piisa uuesti skaneerimisest: sama päring, sama roll, sama rentnik ja sama objekt. Kordustest ei ole kogu testi kordamine.

Mida see nimekiri ei kata

Nimekiri katab API-liidese riskid OWASP-i kategooriate kaupa. Välja jäävad:

  • Toote äriloogika, mida kategooria ei kirjelda: API6 annab raami, aga sinu voog tuleb ise kirja panna, sest risk muutub tööstusharuti.
  • Infrastruktuur, võrk ja pilvekonfiguratsioon: need kuuluvad küberauditi ulatusse.
  • Brauseripoolne osa ja mobiilikliendid: vaata veebirakenduse turvatestimise juhendit.
  • Kolmandate osapoolte süsteemid ise: API10 katab sinu poole, teenusepakkuja oma jääb temale.
  • Koormus- ja mahutestid: need võivad teenust häirida ja vajavad eraldi luba.

Juhend testi ettevalmistamiseks on API turvatestimise lehel; teenuse ulatus lepitakse kokku pentestimise lehel.

Allikad

  • OWASP API Security Top 10 (2023) annab kategooriate numbrid ja nimed.
  • OWASP API Top 10 riskitabel kirjeldab iga kategooria riket.
  • OWASP WSTG 4.2 objektiviidete test soovitab testida vähemalt kahe kasutajaga.
  • CVSS v4.0 spetsifikatsioon eristab ärakasutamise mõõdikud ja mõju teistele süsteemidele.
  • NIST SP 800-115 käsitleb raporti sisu ja paranduse kontrollimist kordustestiga.

Küsimused kontrollnimekirja kohta

Mida see kontrollnimekiri sisaldab?

OWASP API Security Top 10 (2023) tabeli, mis seob iga riski kontrolli ja raportis oodatava tõendiga, ning kordustesti punktid.

Kas API pentest vajab OpenAPI kirjeldust?

See ei ole kohustuslik, kuid OpenAPI või Postmani kogu muudab ulatuse ja otspunktide katvuse kontrollitavaks ning vähendab testimüra.

Kuidas hinnata API pentesti tulemust?

Vaata kinnitatud leidude mõju, tõendeid ja parandussoovitusi, mitte ainult leidude arvu. Oluline on, kas leid on korratav ja kas parandus on kontrollitav kordustestiga.

Kas API pentestiks on vaja kaks rentnikku?

Mitme rentnikuga API puhul jah: ühe rentniku sees saab kontrollida rollipiire, aga rentnike eraldatust näitab alles katse teise rentniku objektile. Ühe rentnikuga süsteemis piisab kahest kasutajast ja erinevatest rollidest.

Mida teha, kui leidu ei õnnestu korrata?

Korda sama päringut sama rolli ja objektiga ning kontrolli, kas käitumine tuleb toote dokumenteeritud reeglist. Kui leid ei kordu, märgitakse see kinnitamata leiuks ja põhjus kirjutatakse raportisse; kinnitamata leidu ei loeta parandatuks.
